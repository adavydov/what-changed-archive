Supabase для агентов: понятные ошибки, миллионы баз и личные данные вне одного приложения

Пол Копплстоун обсуждает с Гарри Таном, Харджем Таггаром и Джаредом Фридманом из YC, как Supabase перестраивается под приложения, создаваемые агентами. Разговор соединяет инфраструктуру баз с практикой использования AI внутри компании и личным проектом памяти Гарри Тана.

Основные мысли

  • Supabase делает возможности панели доступными через код и переделывает CLI для работы агента в изолированной среде.
  • Сообщение об ошибке должно объяснять ремонт: иначе агент может сменить инструмент при ошибке.
  • Копплстоун хранит личные данные отдельно от агента, чтобы разные продукты могли использовать один накопленный контекст.

Пользователем инфраструктуры становится агент

Копплстоун называет около 13 млн регистраций, порядка 50 млн баз под управлением и более миллиона новых баз в неделю. За год он ожидает четырёхкратного роста выручки. Среди создающих приложения становится больше людей без инженерной профессии: участники приводят личное финансовое приложение бывшего fintech-основателя и местный сервис такси, который сделал водитель из Бразилии.

Supabase прошла путь от dashboard к API и затем к работе через код. API, понадобившийся раннему интегратору примерно в 2021 году, позднее оказался полезен конструкторам приложений. Теперь люди реже заходят в панель. Команда требует кодового эквивалента для возможностей интерфейса и переделывает CLI так, чтобы им было удобно пользоваться внутри sandbox. Открытый Postgres и исходники помогают модели разобраться в системе и выбрать её для своей задачи.

Нужно пережить первую ошибку

Попасть в исходный выбор агента — только начало. По дороге он обязательно встретит ошибку, и тогда сообщение сервиса становится частью его способности продолжить работу. Supabase переписывает такие сообщения: они должны объяснять исправление или вести к нужной документации.

Команда проверяет конкретные пользовательские сценарии разными моделями и создаёт навыки для Postgres. Пригодность продукта для агента требует отдельных испытаний использования. Внутри Supabase растут объёмы тестирования и CI. Coding agents прижились без обязательной общей AI-политики: людям дали инструменты, а дальнейшее распространение пошло через полезные результаты коллег.

Огромный кластер и множество маленьких приложений

Инфраструктуре приходится поддерживать две разные задачи. Для большого Postgres-кластера компания развивает Multigres. Для огромного числа лёгких баз Копплстоун обсуждает Turso и будущий Spark. Когда модель создаёт базу под маленькое приложение одного человека, выделенный тяжёлый сервер становится слишком дорогой минимальной единицей.

Чтобы представить будущую нагрузку, он рассматривает сценарий, в котором аудитория ChatGPT создаёт порядка 1,2 млрд новых баз в месяц. Это меняет само инженерное задание: нужно дёшево обслуживать множество небольших попыток и давать удачным проектам расти. Стратегия day one сохраняется, но первый день теперь есть и у стартапа, и у нового личного приложения. Их данные затем растут разными путями.

У личных данных своя жизнь

Один из ведущих сначала хотел хранить всё в Markdown и обращаться к информации через чат. Но реальные личные приложения снова потребовали интерфейсов и баз. Финансы, здоровье, календарь, CRM и документы начинают давать контекст друг другу.

Сам Копплстоун выносит данные из одного агента в отдельное хранилище, к которому могут подключаться разные агенты. Накопленный контекст остаётся у человека, пока интерфейсы меняются. Важной становится долговечная потребность в данных и возможность быстро приспосабливать к ней новые продукты.

Gbrain: поиск и испытания собственной памяти

Гарри Тан описывает Gbrain, где сотни тысяч файлов и десятки гигабайт контекста нужно находить по запросу. Он сочетает Postgres, векторный и графовый поиск, а затем готовит для агента отчёт с нужными страницами. Весь архив не приходится каждый раз помещать в контекст модели.

Из реальных трасс работы Тан собрал собственный набор проверок примерно с 40 категориями, включая эффективность, стоимость и задержку. Агент пробует изменения: удачные проходят по этим проверкам, неудачные попытки сохраняются отдельно. Второй цикл ищет новые категории испытаний. Так личный инструмент получает сразу две линии развития — улучшение поведения и уточнение того, что считать хорошей работой.

Как компания ищет следующую волну

Копплстоун сам пробует создавать приложения разговором и сознательно меньше подсказывает архитектуру. Он хочет прожить тот путь, по которому пойдёт будущий пользователь. Для партнёрских экспериментов компания оставляет свободную инженерную мощность: множество совместных попыток не срабатывает, а отдельные удачные открывают следующую волну спроса.

В конце участники обсуждают небольшие прибыльные вертикальные SaaS. Некоторым всё труднее привлечь Series A, хотя бизнес может обслуживаться малой командой. Отсюда возникает другой взгляд на успех: компании с хорошей экономикой не всегда нужен очередной раунд, даже если венчурная траектория прежде казалась привычной мерой продвижения.
