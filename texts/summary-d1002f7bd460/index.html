How Anthropic ships Claude with Claude: Separating the Brain from the Hands

Три основных вывода

  1. CPU стал ограничением наряду с ускорителями: API, продуктовые сервисы, sandboxing, CI и исследовательские среды делят заранее закупленную мощность. Бюджета уже недостаточно для мгновенного расширения VM. Команда отдельно работает над поставкой и эффективностью, сохраняя требования изоляции.
  2. Команда без исходного опыта Rust создала полный эквивалент Messages API на Rust с помощью Claude. Люди проектировали систему и верификацию; shadow traffic сравнивал ответы старой и новой реализации. По самоотчёту гостей это снизило CPU примерно на 40–50% и время до первого токена на 10–20%. Ранняя реплика ведущего про порядок величины не является итоговой оценкой экономии.
  3. Первый вариант агента целиком запускался в sandbox: нужно было ждать его старта, а сбой среды уничтожал сессию. Отдельный долговечный harness и журнал состояния с создаваемыми по необходимости руками улучшили задержку и восстановление. Безопасность стала ещё одной выгодой того же разделения.

Оригинал

Кто говорит: Кейтлин Лесс и Анджела Цзян, руководители engineering/product Claude Platform; swyx и Алессио Фанелли. Автотранскрипт не размечает говорящих; спорные реплики атрибутируются команде.

Главная мысль: Команда Anthropic показывает, как работа над доступом, API и исполнением превращает более сильную модель в управляемую платформу; дефицит CPU и проверка эквивалентности меняют даже решения о переписывании системы.

  • Во вступлении swyx разбирает свежую S-1: выручка за 12 месяцев на сотрудника выросла с$1.4 млн до$6.6 млн, а квартальная GAAP-маржа достигла 19%. Он связывает это с петлями улучшения модели и инвестиций. Это аналитическое вступление ведущего со ссылкой на отчётность; разговор с гостями записан раньше, после релиза Opus 5.5.
  • В Opus 5.5 команда одновременно работала над ясностью письма и интеллектом на доллар. Новая модель требует изменений вокруг API: модельный релиз включает совместимость интеграции, цену кэша, защиту рассуждений и управление доступом, а не только новые веса.
  • Сохранение thinking-блоков между ходами затрудняет извлечение цепочки рассуждений для дистилляции. Без совместимой замены это могло бы нарушить некоторые пользовательские стратегии compaction. Команда заранее работала с крупными клиентами и open-source harness maintainers и добавила API-компактацию, совместимую с новым ограничением. Гости объясняют защиту прежде всего безопасностью производных моделей.
  • Product и engineering тесно смешивают компетенции, но гости не считают инженерную работу решённой. Работающие на масштабе распределённые системы всё ещё требуют человеческих решений об архитектуре, безопасном выпуске и эксплуатации. При приходе Лесс исходной системой был Python-монолит в одном регионе; затем API расширили на несколько регионов и портировали на Rust. Это история эволюции системы, а не описание её нынешнего состояния.
  • Каждый релиз требует определить online/offline safeguards, правила хранения данных, верифицированные программы cyber и bio. Trust grants проводят право конкретного пользователя на модель или режим через весь стек. Их использовали также для общего отзыва доступа и льготного периода миграции API; это обычная авторизация, специально последовательно встроенная в систему.
  • Продуктовая команда всё чаще выбирает общие примитивы как портфель защит от трудно предсказуемых сценариев. Система доступа, созданная для проверенных исследователей, затем оказалась полезной при снятии модели с публикации и других сменах политики. Гости подчёркивают отличие этого опыта от привычного фокуса только на одном заранее известном use case.
  • Ранний доступ дают прежде всего клиентам с сильными evals, способным быстро вернуть конкретные ошибки. Их собственные harnesses открывают поведение, которого не видно во внутренних продуктах Anthropic. Позитивный отзыв подтверждает ожидания; особенно полезен негативный, по которому можно изменить вариант модели до релиза.
  • Пользователи по-разному понимают инициативу и лень агента: одним нужно закончить задачу, другим пока только обсудить. Команда пока комбинирует judgement, настройки effort и разные defaults по продукту и сегменту; полноценная персонализация остаётся нерешённой. Управляемый harness снимает с клиента часть работы по сочетанию параметров и миграции между моделями.
  • Managed Agents даёт API для определения агента и запуска сессии поверх готовой инфраструктуры. Dreaming реализован ещё одним управляемым агентом: он изучает предыдущее исполнение и записывает память. Базовый harness намеренно прост; стратегии best-of-N, verifier и общая память строятся сверху. Планы раскрыть дополнительные примитивы не равны уже выпущенным функциям.
  • Гости советуют начинать с простых проверок и наращивать их набор, а не бесконечно выбирать идеальную систему при нуле работающих evals. Ведущие описывают инженерную работу как исследование: формализовать цель, измерить и выяснить, ошиблись ли оценка, среда или модель. Агенты помогают писать и анализировать такие проверки.

Ранняя реплика ведущего про порядок величины не является итоговой оценкой экономии.
  • Миграцию намеренно ограничили чистым портом без новых функций, пока основная команда продолжала развивать API; статические проверки ловили расхождение двух реализаций. Хранение состояния разговора и дальнейшую перестройку оставили следующему этапу. Работа в трёх облаках мешает полагаться на одну специфическую форму вычислений.

  • Секреты хранятся отдельно; агент видит placeholder, а исходящий proxy подставляет нужный credential. Domain allowlists ограничивают сеть sandbox. Гости различают инциденты при обучении и production с дополнительной архитектурой и safeguards; это описание их защиты, не доказательство невозможности любых инцидентов.
  • Проверка безопасности может прервать текущую работу или перевести на слабую модель. В API клиент может управлять fallback; гости признают неудобство и обсуждают будущий более цельный опыт с динамическим effort. Маршрутизация сложна также потому, что сложность и намерение задачи неизвестны заранее.
  • В некоторых задачах дополнительный интеллект уже насыщается; гости видят потенциал в долго работающих агентах и сложных научных либо инженерных задачах, которые прежде не удавалось перебрать. Часть узких корпоративных процессов уже автоматизируется, часть остаётся незрелой.
  • За качество сгенерированного документа отвечает отправитель: непрочитанный текст переносит труд на получателя. При этом признаки модельного стиля сами по себе не доказывают плохое качество. В коде больше внимания уходит архитектуре и проверкам; ускорение реализации не отменяет исследования потребностей и осмысленного выбора функций.
  • Гости обсуждают чтение как интеллектуальную тренировку, письмо как сжатие мысли и конфликт между сосредоточенной работой и постоянным Slack. Важная функция руководителя — снять трудное блокирующее решение, даже когда за день не появился отдельный документ; постоянная переписка всё же требует границ внимания.
  • У платформы и Claude Code отдельные DevRel-команды из-за разных аудиторий. DevRel платформы делает обучение, evals, примеры и Claude API skill: накопленные лучшие практики получает сам coding agent. Ведущие предлагают разделить публичного эксперта и production-команду, которая помогает ему передавать опыт с небольшой затратой времени.
  • В финале гости предлагают повторно попробовать задачи, которые раньше не окупались по токенам, и многоагентные схемы. Их два архитектурных условия — возможность параллельной работы с общей средой и асинхронные субагенты, не блокирующие друг друга. Остальную организацию предлагают экспериментально поручать модели; это рекомендация гостей, не гарантия результата.
  • Memory, Dreaming и skills остаются развиваемыми возможностями, но команда описывает смену ближайшего приоритета и распределения ресурсов в пользу безопасного доступа к моделям. Сообществу намерены дать примитивы, на которых оно сможет строить собственные способы памяти и контекста. Это не объявление о прекращении Dreaming и не только описание устройства самой функции.
