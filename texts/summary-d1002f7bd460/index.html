Как Anthropic строит Claude Platform: доступ, управляемые агенты и переписывание API на Rust

Руководители engineering и product Claude Platform Кейтлин Лесс и Анджела Цзян рассказывают, что приходится менять вокруг модели, чтобы ею можно было пользоваться на большом масштабе. В беседе с swyx и Алессио Фанелли они проходят путь от API и доступа до устройства агентов, нехватки CPU и переноса системы с Python на Rust.

Основные мысли

  • Выпуск модели включает API, кэш, работу с контекстом и доступ: эти части нужно менять согласованно с клиентами.
  • Перенос Messages API на Rust снизил потребление CPU примерно на 40–50% при проверке ответов на теневом трафике.
  • Долговечный управляющий контур агента отделили от запускаемых по необходимости sandbox-сред, сохранив состояние между сбоями.

Релиз модели выходит за пределы новых весов

В Opus 5.5 команда одновременно улучшала ясность письма и интеллект на доллар. Модельный релиз затрагивает совместимость интеграций, цену кэша, защиту рассуждений и управление доступом. Например, сохранение thinking-блоков между ходами затрудняет извлечение рассуждений для дистилляции, но требует совместимого способа сжимать длинный разговор.

Поэтому команда заранее работала с крупными клиентами и разработчиками открытых harnesses, а затем добавила API-компактацию. Защиту рассуждений гости связывают прежде всего с безопасностью производных моделей.

В отдельном вступлении к подкасту swyx разбирает свежую S-1: выручка за двенадцать месяцев на сотрудника выросла с $1,4 млн до $6,6 млн, квартальная GAAP-маржа достигла 19%. Он связывает эти показатели с циклами улучшения моделей и инвестиций. Сам разговор с гостями был записан раньше, после выпуска Opus 5.5.

Один механизм доступа для разных ситуаций

Для каждого релиза приходится определять online- и offline-защиту, правила хранения данных, доступ проверенных cyber- и bio-исследователей. Trust grants проводят право конкретного пользователя на модель или режим через весь стек.

Созданная для проверенных исследователей система затем пригодилась при снятии модели с публикации, отзыве доступа и предоставлении льготного периода для миграции API. Команда всё чаще выбирает общие примитивы, пригодные для нескольких будущих сценариев. Это помогает там, где заранее известного единственного use case недостаточно.

Ранний доступ особенно ценен для клиентов с хорошими собственными evals. Их harnesses показывают поведение, которого команда не встречает во внутренних продуктах Anthropic. Негативный отзыв полезен тем, что указывает на конкретную ошибку, которую ещё можно исправить до релиза.

Почему инженерная работа сохраняется

Product и engineering тесно смешивают компетенции, однако распределённой системе по-прежнему нужны человеческие решения об архитектуре, безопасном выпуске и эксплуатации. Когда Лесс пришла в компанию, исходная система была Python-монолитом в одном регионе. Затем API расширили на несколько регионов и перенесли на Rust.

CPU стал ограничением наряду с ускорителями. API, продуктовые сервисы, sandboxing, CI и исследовательские среды делят заранее закупленные мощности. Наличие бюджета уже не позволяет мгновенно добавить нужное количество виртуальных машин, поэтому приходится одновременно работать над поставкой и эффективностью.

Как переносили Messages API

Команда без исходного опыта Rust с помощью Claude создала полный эквивалент Messages API. Люди проектировали систему и способ проверки, а shadow traffic сравнивал ответы старой и новой реализации. Гости называют снижение потребления CPU примерно на 40–50% и времени до первого токена на 10–20%.

Миграцию сознательно ограничили чистым переносом без новых функций. Основная команда тем временем продолжала развивать API, а статические проверки помогали находить расхождения двух реализаций. Хранение состояния разговора и дальнейшую перестройку оставили следующему этапу. Работа в трёх облаках дополнительно ограничивает зависимость от одной специфической формы вычислений.

Отделить состояние агента от его рук

Сначала весь агент запускался внутри sandbox: пользователь ждал старта среды, а её сбой уничтожал сессию. Затем команда выделила долговечный harness и журнал состояния, а исполняющие среды стала создавать по необходимости. Управляющий контур сохраняется, даже когда отдельные «руки» приходится перезапустить. Это улучшило задержку, восстановление и безопасность.

Секреты хранятся отдельно от среды агента. Внутри он видит placeholder, а исходящий proxy подставляет нужные учётные данные. Domain allowlists ограничивают сетевые обращения sandbox.

Managed Agents предоставляет API для определения агента и запуска сессии поверх готовой инфраструктуры. Dreaming устроен как ещё один управляемый агент: он изучает прошлое исполнение и записывает память. Базовый harness намеренно прост; best-of-N, проверяющие агенты и общая память строятся поверх него. В ближайшем распределении ресурсов команда усилила безопасный доступ к моделям, продолжая развивать память и примитивы для работы с контекстом.

Намерение пользователя и проверка результата

Пользователи по-разному воспринимают инициативу агента. Одному нужно закончить задачу, другому — пока только обсудить её. Команда сочетает judgement, effort и разные настройки по продуктам и сегментам. Управляемый harness берёт на себя часть работы по согласованию параметров и переходам между моделями.

Проверка безопасности иногда прерывает работу или переводит её на менее сильную модель; в API клиент может управлять fallback. Команда обсуждает более цельный опыт с динамическим effort. Это трудно ещё и потому, что сложность и намерение задачи неизвестны заранее.

С evals гости советуют начинать с простых работающих проверок и постепенно расширять набор. Сама инженерная работа становится исследованием: сформулировать цель, измерить результат и понять, где ошибка — в оценке, среде или модели. Агенты помогают и писать проверки, и разбирать их результаты.

Куда уходит человеческое внимание

За отправленный сгенерированный документ отвечает отправитель. Если он его не прочитал, работу по проверке получает адресат. При этом узнаваемый модельный стиль сам по себе ничего не говорит о качестве содержания. В коде больше внимания теперь требуют архитектура и проверки, а ускорившаяся реализация оставляет работу по исследованию потребностей и выбору функций.

Гости обсуждают чтение как интеллектуальную тренировку, письмо как способ сжать мысль и конфликт сосредоточенной работы с постоянным Slack. Важный результат руководителя иногда состоит в снятом трудном блокирующем решении, даже если к концу дня не появился отдельный документ.

У Claude Platform и Claude Code разные DevRel-команды, потому что они обращаются к разным аудиториям. Команда платформы делает обучение, примеры, evals и Claude API skill, через который лучшие практики получает сам coding agent. Ведущие предлагают помогать публичному эксперту отдельной production-командой, чтобы передача опыта требовала меньше его времени.

Следующие задачи для агентов

В некоторых узких задачах прибавка интеллекта уже даёт всё меньше. Команду интересуют долго работающие агенты и сложные научные или инженерные задачи, где раньше нельзя было перебрать достаточно вариантов. В финале гости предлагают заново пробовать работу, которая прежде не окупалась по токенам.

Для многоагентных схем они выделяют два архитектурных условия: параллельную работу с общей средой и асинхронных субагентов, которые не блокируют друг друга. Остальную организацию предлагают искать экспериментами вместе с моделью.
