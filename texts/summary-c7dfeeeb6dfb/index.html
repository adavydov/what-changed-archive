Claude Code: как сделать проверку агентов сходящейся

Эдди Османи, Морган Уэстли Лант и Цин Ван описывают процесс разработки Claude Code. После роста покрытия и глубины проверок команда стала оптимизировать суммарное время людей — и на ревью, и на исправление последствий — при ограничениях по откатам и инцидентам.

Основные мысли

  • С июня по сентябрь число слитых PR Claude Code более чем удвоилось, а доля отменённых изменений снизилась более чем на 40%, по данным команды.
  • Глубину проверки и число людей задают риск изменения, чувствительные пути и доверие к автору; одобрение относится к конкретному commit.
  • После ограничения повторных ревью доля PR с одной итерацией выросла с 65% до 78%, а среднее число проверок до прохождения снизилось с 2,08 до 1,32.

Что команда считает экономией

Авторы начинают с масштаба агентной разработки. В отдельном репозитории Claude Code с июня по сентябрь число принятых PR более чем удвоилось, а доля откатов снизилась более чем на 40%. Они отдельно приводят рост изменений в общем monorepo Anthropic с 2500 в день в мае до более 30000 в сентябре.

Цель — сохранить человеческое внимание для решений, в которых оно даёт наибольшую пользу. Снижение времени чтения не считается успехом, если та же работа возвращается через поломки. Команда отслеживает число человеческих согласований, включая медиану и 95-й перцентиль, комментарии и ожидание человека, а также откаты и инциденты. Ревью должно находить ошибки и распространять понимание кода; для второй задачи появляются отдельные способы. Для большинства PR команда стремится обходиться не более чем одним человеком, которым может быть сам автор, без увеличения числа откатов и инцидентов.

Проверять работу до появления PR

Агенту дают исполняемую проверку — тесты, сборку или скриншот для сравнения — и требуют показать результат. Затем другой агент читает diff в свежем контексте. Дополнительные skills ищут баги, упрощают изменение и проверяют поведение целиком. Повторяющуюся проблему команда переносит в правило или инструмент у источника.

Короткий CLAUDE.md описывает цели, стек и соглашения и ссылается на другие документы. REVIEW.md от владельцев кода объясняет, какие ошибки важны в конкретной части, где не искать, как ограничить мелкие замечания и почему находке нужны файл и строка. Отдельно проверяется, следует ли сам ревьюер этим указаниям.

Как находки проходят проверку

Каждый PR до человека получает AI-review по diff, репозиторию и заявленному намерению. Несколько агентов параллельно ищут баги, а другая группа проверяет находки голосованием. Замечания о стиле и уборке фильтруются; оставшиеся ранжируются по важности и отделяются от уже существовавших ошибок. После запуска такого ревью доля внутренних PR с содержательными комментариями выросла с 16% до 54%.

Каждая находка должна быть исправлена или закрыта с объяснением. То же относится к отдельному security-review: открытый вопрос любого из этих проверяющих блокирует merge. Кроме них обязательны lint, типы, тесты по платформам, сборка и упаковка. В PR записывают проверку и способ отмены; инициатор изменения подтверждает эту работу.

Когда требуется человек

Классификатор определяет риск самого изменения. Низкий риск может пройти без отдельного человеческого одобрения после автоматических проверок, средний требует одного человека, высокий двух. Второй классификатор проверяет, не нужен ли дополнительный человек вопреки общему уровню. Для чувствительных путей и CI-workflow действуют обязательные правила.

Облегчённый путь доступен только доверенным авторам. У остальных нужен второй человек, а одобрение агента никогда не занимает человеческое место. Человек, поручивший код агенту, отвечает за него и считается одним из необходимых ревьюеров. Одобряется конкретный commit: новые изменения, за которые система не может поручиться, требуют повторного решения.

Как пережить ошибку после слияния

Merge queue повторно запускает проверки на актуальной main с применённым изменением, чтобы две по отдельности удачные правки не сломали общий результат. Новое поведение обычно сначала включают флагом сотрудникам Anthropic, затем в канале latest, позже в stable.

Автор и дежурный наблюдают за результатом. Флаг можно выключить без новой поставки, сломанную сборку откатить. Автоматических выключателей, которые ужесточают согласования при росте откатов или инцидентов, у команды пока нет; инженеры хотят получить их до дальнейшего расширения merge без человека. Авторы предпочитают быстро замечать и исправлять ошибки, сохраняя полезную скорость работы.

Как улучшают ревьюера и заставляют его заканчивать

Первый приоритет команды — находить настоящие ошибки; сокращение числа раундов идёт следом. Инцидент или откат становится примером для ежедневной проверки. Знающие код инженеры подтверждают ошибку и её место, затем каждый новый prompt, инструмент или модель ревьюера оценивается на накопленном наборе. Шум измеряют по реакции людей на комментарии и по запуску на заведомо чистых PR: особенно важно заметить совет, который подтолкнул бы к вредной правке.

У автора-агента мелкое замечание стоит дороже: он исправляет его, создаёт commit и запускает новый круг. Однажды PR за ночь прошёл более пятидесяти раундов. Анализ git blame показал, что около 59% вновь отмечаемого кода присутствовало ещё на первом проходе: проверяющий находил новые старые проблемы понемногу.

Команда стала после трёх раундов просить автора пересмотреть подход, после первых проходов проверять только новый diff, указывать целый класс бага и не повторять опубликованное. После этих изменений доля внутренних PR, проходящих за один круг проверки и исправления, выросла с 65% до 78%; доля требующих пяти и более упала с 8,9% до 1,5%, среднее число ревью с 2,08 до 1,32. Старый код при этом продолжают проверять отдельными ночными запусками.

Как люди понимают код и сохраняют ответственность

Люди определяют, нужно ли вообще строить предложенную функцию, выбирают направление, оценивают архитектурные шаблоны и рискованные области и читают свидетельства проверок. Для изучения модуля вместо чтения всех мелких diff они просят Claude подготовить объяснение нужного среза текущего кода; иногда создают наглядный обучающий артефакт. Открытая работа в Slack помогает коллегам видеть решения и вовремя предложить другой путь.

Норма «слил — отвечаешь» опирается на небольшие изменения, обратимость, быстрые сигналы регрессии и помощь команды. Автор обычно лучше всего понимает контекст исправления, а разбор инцидента ищет системную причину. Если направление сомнительно, его стараются обсудить рано в общей ветке: дешёвую в создании правку легче закрыть, чем защищать уже завершённый PR.

Где заканчивается этот внутренний процесс

В публичном Code Review продукт публикует находки, а одобрение PR остаётся человеческим решением. Собственные репозитории Anthropic идут дальше и позволяют владельцам определить, какие малорисковые изменения принимаются на автоматических проверках. Авторы завершают тем же критерием: меньше человеческого времени на изменение при сохранении качества по откатам и инцидентам.
