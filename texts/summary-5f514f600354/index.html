Eightfold: как связать работу агентов с поддержкой, разработкой и выпуском продукта

Инженеры Eightfold, платформы для найма и управления сотрудниками крупных компаний, разбирают 16 месяцев внедрения AI внутри своей разработки. Они проходят через общие навыки, поддержку, дежурства, создание функций и безопасность, объясняя, где агент действует сам и в какой момент решение принимает человек.

Основные мысли

  • Быстрый ответ поддержки может удлинить передачу человеку; Eightfold меняет маршрутизацию по результатам закрытых обращений.
  • У дежурного агента закончились AI-кредиты, и он больше часа молча не разбирал alerts: бюджет стал частью контроля доступности.
  • Технический агент предлагает 2–4 варианта дизайна, человек выбирает, отдельный Verify Agent проверяет реализацию до человеческого merge.

Единицей результата становится законченная работа

За 16 месяцев Eightfold сократила медианное время прохождения эпика примерно на две трети. Авторы объясняют подход через конкретные единицы: разобранное обращение, исследованный alert, проверенный pull request и выпущенная функция. Число строк на инженера выросло в 4,2 раза с апреля 2025 года, но команда видит в нём и массовые сгенерированные коммиты. Поэтому полезность агента проверяют по результату и качеству каждой задачи, а токены учитывают как расход.

У каждого агента узкая работа, понятные пределы и человек, отвечающий за результат. Самостоятельные действия разрешают там, где накопленные случаи показали достаточную надёжность. Эти правила дальше проявляются по-разному: в поддержке важна маршрутизация, в разработке — выбор дизайна и проверка, в безопасности — возможность реально воспользоваться найденной уязвимостью.

Общее знание распространяется как версионируемый продукт

Команда упаковала способы работы в plugins и skills внутреннего marketplace. Правило обновляют в одном месте, а новая версия автоматически доходит до пользователей. Трассы показывают, какие навыки используют команды и где они ломаются. Если навык тратит много токенов на предсказуемые операции, эти шаги переносят в обычные скрипты, оставляя модели суждение.

Такой подход вышел за пределы engineering. Плагин подготовки business-value review собирает презентацию из продуктовых данных; команда оценивает экономию в 25 часов на сотрудника клиентской команды в месяц. Другой плагин соединяет эпик, проектные документы и код в документацию функции, проверяя утверждения по коду до ревью технического писателя. На схеме Eightfold указывает экономию двух недель времени писателя на документ за последние 90 дней.

Helixa проверяет объяснение по тому, чем закончилось обращение

Helixa исследует данные, настройки, логи и код, находит причину обращения поддержки и предлагает исправление. При внутренней оценке уверенности выше 95% она может сразу ответить клиенту; остальные случаи передаёт инженеру вместе с анализом. Право прямого ответа появилось после месяцев проверки. Каждый анализ сравнивают с фактическим разрешением закрытого обращения; доля оценённых как правильные или вероятно правильные выросла примерно с 59–65% до 72–75%.

Автоответы ежедневно сверяют с завершёнными случаями, а повторяющиеся ошибки превращают в предложения по исправлению. Среди автоответов с понятным клиентским исходом 82% либо решили проблему, либо задали верное направление, которое затем уточнил человек. В графике 7106 закрытых обращений, открытых с 16 апреля по 3 октября 2026 года, медиана первого ответа составляет 24 минуты для 3293 случаев с ответом AI и 7,1 часа для 3813 без него. Автоматические подтверждения короче двух минут исключены; авторы отмечают, что AI чаще получает обычные случаи.

Но быстрое начало не гарантировало быстрого завершения. Когда инженеру приходилось переделывать ответ AI, обращение дольше стояло в очереди передачи. Следующее улучшение команда поэтому видит в немедленной отправке таких случаев человеку.

Бюджет агента стал частью надёжности дежурства

Получив production-alert, дежурный агент следует playbook команды, сам запускает запросы, собирает логи из разных регионов и пишет вероятную причину и следующий шаг в обсуждение инцидента. Решение остаётся за on-call инженером. Новый markdown-playbook достаточно добавить в репозиторий: после merge агент использует его на следующем alert без отдельного развёртывания.

Один ранний сбой показал неожиданную зависимость. Баланс AI-кредитов закончился, агент остановился молча, и production-alerts больше часа оставались без первичного разбора. После этого появились проверки здоровья агента, проверка бюджета перед запуском и предупреждения о низком остатке.

Человек выбирает между решениями, агент проверяет реализацию

Dev pipeline начинается с эпика в системе задач. TL Agent предлагает 2–4 варианта дизайна с компромиссами, чтобы человек действительно выбрал подход, а не автоматически одобрил единственный готовый ответ. Затем Dev Agent реализует его частями. Отдельный Verify Agent оценивает pull request по критериям выбранного дизайна; провал возвращает работу разработчику ещё до человеческого ревью. Последний merge выполняет владелец кода.

Полный цикл команда проверила от начала до конца, заново построив одну уже выпущенную функцию по её эпику. В безопасности агент параллельно проверяет исправления и выясняет, достижим ли уязвимый код и можно ли им воспользоваться. Перед выпуском эпик получает threat model и агентный penetration test; по данным команды 86% шума ложных уязвимостей отсеивается до человека. Для части работы Eightfold испытывает более дешёвые открытые модели на том же качестве результата.
